# 一次操作只起一次运行（M-280）

本文件属于 `mouse9527/multica` fork（上游没有）。开关 `run_dedup_v1`（环境变量 `FF_RUN_DEDUP_V1=true`），默认关闭；关闭时与上游行为一致。

## 要解决的重复

同一个智能体在同一张 issue 上，因为一次操作被启动两次：

1. **先指派、再改状态**：操作者先把 issue 指派给智能体，紧接着（另一次请求，相隔约 200ms）把状态改到由这个智能体处理的工作流步骤。指派触发的运行立刻被领取，绑定的是旧步骤；交接又排了一个绑定新步骤的运行。第一个运行拿着旧步骤的说明干活，最后改状态时被平台按「步骤已移动」拒绝，第二个运行只是来补这次状态变更。
2. **先改状态、同一秒再 @**：改状态触发的运行立刻被领取，随后 @ 该智能体的评论占了另一个排队槽位（按评论线程分槽），排在第一个运行后面，等它跑完才开始，读到的东西第一个运行都处理过了。

完成时的补发（上游 multica-ai/multica#7237）也是同一类：第一个运行领取后一两秒内到的评论，不在它领取时的送达回执里，运行结束后会被补发成一个新运行。

## 判断依据

运行在**领取**时生成说明（步骤、交接说明、评论增量），领取之后说明就固定了；但智能体要等进程起来才第一次读 issue 和评论。按我们实例上 92 对重复运行统计，领取到第一次读 issue 或评论最短 5.1 秒，中位数 12 秒。所以：

- **领取后 3 秒内**到达的输入，运行一定读得到（`forkRunClaimGrace`）；
- 领取前已经存在的输入，领取时的评论增量会算进去，运行也读得到。

## 规则

### 交接取代刚领取的运行（场景 1）

工作流交接要给智能体排运行前（`dispatchIssueRun` 的钩子），对这个智能体在这张 issue 上、绑定在 issue 刚离开的步骤上的运行：

- **还在排队**：改绑到新步骤（`ForkRebindQueuedRunsToStep`）。它领取时拿到的是新步骤的说明；交接自己的入队和它占同一个槽位时直接并进去。
- **3 秒内刚领取**：取消（`failure_reason = superseded_by_handoff`），由交接排的新运行接替。它还没读过任何东西；它带的触发评论在新运行领取前就在 issue 上，新运行会读到。
- **领取超过 3 秒**：可能已经在干活，不动，交接的运行照旧排在后面。

只处理普通的指派和评论运行（`trigger_evidence_kind` 为 `issue_assignment` 或 `comment`），不碰重跑、系统重试、wakeup、小队负责人的运行。请求里带了旧客户端的交接说明（`handoff_note`）时不处理，因为那段说明只跟着新运行走。

### 运行成功后并掉被它覆盖的排队运行（场景 2 与补发）

运行成功完成、上游的完成补发做完之后（`CompleteTask` 的钩子），同一智能体在同一 issue 上排队中的运行，满足下面全部条件就取消，记为并入这次运行（`failure_reason = folded_into_prior_run`，`error` 写明并入哪个运行）：

- 两个运行都是普通的指派或评论运行；排队的这个不是重跑、重试、wakeup，没有旧式交接说明；小队、负责人身份、评审的 HEAD（`head_sha`）一致。
- **输入都在窗口内**：窗口是「完成的运行创建前 15 秒」到「它领取后 3 秒」。指派类输入看排队运行的创建时间；评论类输入看每条触发评论和合并进来的评论的创建时间。被补发出来的运行创建得晚，但它的评论如果在窗口内，同样并掉。
- **领取后才到的评论**，只有在完成的运行没被告知「可以跳过读评论」时才算读到。上游只对「评论触发、续接上一次会话、且上次以来没有新评论」的领取给出这种豁免；判断用的是同一个计数口径（排除它自己的评论和它的触发评论），按上一次开始的运行算，只会更保守。
- **窗口里 issue 没变**：从完成的运行创建到窗口结束，没有状态、指派人、标题、描述变更（`activity_log`）。有变更说明它领取时看到的步骤或内容和排队运行看到的不同，排队运行保留。

条件检查写在同一条 `UPDATE` 里（`ForkFoldCoveredQueuedRuns`），排队运行如果同时被并入一条新评论，会按新的行重新判断，新评论不会被一起取消掉。

**不会被并掉的**：领取 3 秒后才到的评论；豁免了读评论的运行领取之后到的评论；窗口内 issue 状态、指派、标题、描述有变化时的任何排队运行；运行失败或被取消（只有成功完成才并）；别的智能体、别的 issue 的运行。

## 已知局限

- 交接取代刚领取的运行时，如果新运行随后入队失败（例如工作区要求归因失败即拒绝），被取代的运行已经取消。新旧运行的入队检查几乎相同，前一个几秒前刚通过，实际很难出现。
- 排队中的**评论线程**运行被交接改绑后，交接自己的运行占的是另一个槽位，仍会单独排一次；完成时因为窗口里有状态变更，不会并掉。这需要交接发生时第一个运行还在排队，比较少见。
- 运行记录的 attribution 仍显示委托链源头的成员，看不出实际操作的是哪个智能体（Issue 里的 C 项，没做，另行评估）。
- 被取消的运行在界面上显示原始的 `failure_reason` 值（客户端对未知值原样显示），说明在 `error` 里。
