# 一次操作只起一次运行（M-280）

本文件属于 `mouse9527/multica` fork（上游没有）。开关 `run_dedup_v1`（环境变量 `FF_RUN_DEDUP_V1=true`），默认关闭；关闭时与上游行为一致。

## 要解决的重复

同一个智能体在同一张 issue 上，因为一次操作被启动两次：

1. **先指派、再改状态**：操作者先把 issue 指派给智能体，紧接着（另一次请求，相隔约 200ms）把状态改到由这个智能体处理的工作流步骤。指派触发的运行立刻被领取，绑定的是旧步骤；交接又排了一个绑定新步骤的运行。第一个运行拿着旧步骤的说明干活，最后改状态时被平台按「步骤已移动」拒绝，第二个运行只是来补这次状态变更。
2. **先改状态、同一秒再 @**：改状态触发的运行立刻被领取，随后 @ 该智能体的评论占了另一个排队槽位（按评论线程分槽），排在第一个运行后面，等它跑完才开始，读到的东西第一个运行都处理过了。

## 原则：不猜运行读到了什么

运行在**领取**时生成说明（步骤、交接说明、评论增量），领取之后说明就固定了。领取之后才到的输入，运行可能读到，也可能没读到，没有证据，所以**一律不算已覆盖**。去重只用两种不依赖读取时机的办法：

- **取代**：新触发在智能体领取后 3 秒内到达时，取消那个刚领取的运行，由新触发的运行接替。新运行在所有输入都已存在之后才被领取，它的领取本身就带着全部输入，不会丢任何东西。这只对输入都在 issue 上的运行成立：运行自己带着的东西（旧客户端的交接说明 `handoff_note`、强制新会话 `force_fresh_session`）替代运行拿不到，所以带这两样的运行**从不取代**（交接和评论两条路径都一样）。取代的代价只是旧运行做过的事要重做；按我们实例上 92 对重复运行统计，领取到第一次读 issue 或评论最短 5.1 秒、中位数 12 秒，3 秒内的运行通常还什么都没做。3 秒（`forkRunClaimGrace`）只决定「取消哪个」，不决定「哪个输入算读过」。
- **并入**：运行成功完成后，只并掉输入**确实送到**它的排队运行：在它的送达回执（`delivered_comment_ids`）里，或者在它被领取时就已经在 issue 上。

## 规则

### 交接取代刚领取的运行（场景 1）

工作流交接要给智能体排运行前（`dispatchIssueRun` 的钩子），对这个智能体在这张 issue 上、绑定在 issue 刚离开的步骤上的运行：

- **还在排队**：改绑到新步骤（`ForkRebindQueuedRunsToStep`）。它领取时拿到的是新步骤的说明；交接自己的入队和它占同一个槽位时直接并进去。
- **3 秒内刚领取**：取消（`failure_reason = superseded_by_newer_trigger`），由交接排的新运行接替。
- **领取超过 3 秒**：可能已经在干活，不动，交接的运行照旧排在后面。

请求里带了旧客户端的交接说明（`handoff_note`）时不处理，因为那段说明只跟着新运行走；被取代的一方带着交接说明或强制新会话时也不取消。

### 评论取代刚领取的运行（场景 2）

评论要给智能体排运行前（`triggerTasksForComment` 的钩子，在「指定发给运行中的回合」处理之后），对这个智能体在这张 issue 上、在评论发出前 3 秒内被领取的运行，如果它不在任何评论线程里（指派、交接运行），或者就在这条评论所在的线程里，取消它，由评论的运行接替。在别的线程里的运行有自己要回复的线程，不动；带交接说明或强制新会话的运行不动。小队负责人的触发不处理。

### 运行成功后并掉被它覆盖的排队运行

运行成功完成、上游的完成补发做完之后（`CompleteTask` 的钩子），同一智能体在同一 issue 上排队中的运行，满足下面全部条件就取消，记为并入这次运行（`failure_reason = folded_into_prior_run`，`error` 写明并入哪个运行）：

- 两个运行都是普通的指派或评论运行；排队的这个不是重跑、重试、wakeup，没有旧式交接说明；小队、负责人身份、评审的 HEAD（`head_sha`）一致。
- **输入都送到了**：每条触发评论和合并进来的评论，要么在完成运行的送达回执里，要么创建于「完成运行创建前 15 秒」到「它被领取」之间（领取时就在 issue 上，领取的评论增量或要求的评论扫描会包括它）；没有触发评论的排队运行，创建时间也要在这个区间里。**领取之后发的评论不算**，不管隔了多久。
- **领取时 issue 和排队运行创建时一样**：从完成运行创建到它被领取，没有状态、指派人、标题、描述变更（`activity_log`）。

条件检查写在同一条 `UPDATE` 里（`ForkFoldCoveredQueuedRuns`），排队运行如果同时被并入一条新评论，会按新的行重新判断。

**不会被取消或并掉的**：领取后才到的评论的运行（包括上游完成补发出来的）；在别的评论线程里的运行；领取超过 3 秒的运行；运行失败或被取消时它覆盖的排队运行；别的智能体、别的 issue 的运行。

## 已知局限

- 取代后如果新运行入队失败（例如工作区要求归因失败即拒绝），被取代的运行已经取消。新旧运行的入队检查几乎相同，前一个几秒前刚通过，实际很难出现。
- 被取代的运行如果在 3 秒内已经做了事（比如发了评论），新运行会再做一遍。按统计没有出现过。
- 上游 multica-ai/multica#7237 说的完成补发：运行领取后才到的同线程评论，运行结束后仍会补发一次。没有读取证据，所以保留；但通过真实评论路径发、且在领取后 3 秒内的，评论那一刻就已经取代了旧运行，不会走到补发。
- 运行记录的 attribution 仍显示委托链源头的成员，看不出实际操作的是哪个智能体（Issue 里的 C 项，没做，另行评估）。
- 被取消的运行在界面上显示原始的 `failure_reason` 值（客户端对未知值原样显示），说明在 `error` 里。
